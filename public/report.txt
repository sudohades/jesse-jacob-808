1.2 Where design tokens originate
Origin chain:

Palette tokens: defined directly in :root in globals.css:
--frozen-lake-*, --lavender-grey-*, --carbon-black-*, --bright-amber-*, --dark-amethyst-*
Semantic tokens: mapped in :root and .light in globals.css:
--background, --foreground, --card, --primary, --muted, --accent, --border, --ring, etc.
“Design token names” for Tailwind consumption:
@theme inline { --color-background: var(--background); ... }
Also fonts + radii + glass-related vars are defined in @theme inline.
1.3 Where semantic tokens are created
Semantic tokens are created in globals.css under:

:root (dark default semantics)
.light (light overrides)
Examples:

--primary, --secondary, --muted, --accent, --destructive
--border, --input, --ring
--surface-* and glass material system vars (--glass-opacity-*, --glass-blur etc.)
1.4 How Tailwind consumes them
Tailwind consumes via the @theme inline { ... } block which maps CSS custom properties into Tailwind’s theme system:

--color-background → Tailwind bg-background
--color-foreground → Tailwind text-foreground
--radius-* and font variables are also mapped for consistent usage.
Additionally, custom classes in @layer base are used directly (not via Tailwind config).

1.5 Where component styles are defined
Two layers:

Token + utility layer in globals.css
glass surfaces
seam divider primitives
base typography utilities
generic transitions
Component-specific composition
E.g., SiteHeader uses glass-matte border-b border-border
Homepage uses glass-matte + explicit hover shadow.
1.6 Where pages override component styles
Predominantly via:

Tailwind class composition inside pages
Example: homepage cards:
first two cards add seam-divider seam-divider-h md:seam-divider-v
all cards add glass-matte p-8 ... hover:shadow-card
No major “override by CSS selectors” occurs; it’s composition-by-class.

1.7 Where inline styling exists
Reveal.tsx: uses inline style to apply transitionDelay:
style={{ transitionDelay: ${delay}ms, ...style }}
InteractiveText (not yet integrated into pages shown): inline style transforms/opacity on hamburger-like lines.
app/page.tsx: no inline style (only classes).
1.8 Where duplication exists
High-confidence duplications:

Glass logic duplication:
Glass styling exists as two separate utilities .glass-matte and .glass-floating.
Some glass usage patterns still combine Tailwind shadows/borders rather than a unified “surface primitive”.
Navigation link styling duplication by variant:
SiteNav has separate linkClassName strings for horizontal vs vertical.
Card hover + transition duplication:
Homepage manually sets transitions/shadow; other surfaces/cards might do the same elsewhere.

3. Glassmorphism System
3.1 Exact implementation (centralized in globals)
Glass effect is centralized as CSS utilities in app/globals.css:

.glass-matte
Mechanics:

background: var(--surface-elevated)
backdrop-filter: blur(var(--glass-blur)) and -webkit-backdrop-filter
border: 1px solid var(--border-surface)
position: relative
pseudo-element:
.glass-matte::before
fills inset
background: var(--highlight-subtle)
opacity: 0.5
.glass-floating
Mechanics:

background: var(--surface-floating)
backdrop-filter: blur(var(--glass-blur))
border: 1px solid var(--border-elevated)
pseudo-element:
::before with var(--highlight-edge) and opacity: 0.6
3.2 Borders / overlays / shadows composition
Glass border is token-driven (--border-surface, --border-elevated)
Shadows are not intrinsically part of glass utilities:
homepage cards add hover:shadow-card and some components add hover:shadow-soft etc.
Overlays:
texture noise is applied at page level (texture-subtle), affecting perceived glass richness
.hero-overlay is gradient-based overlay animation (not glass utility)
3.3 Where glass is used
High confidence:

SiteHeader: className="... glass-matte border-b border-border"
SiteFooter: className="... border-t border-border glass-matte"
Homepage cards: multiple divs use glass-matte
InteractiveText popup: uses glass-floating p-4 shadow-soft ...
3.4 Centralized or duplicated?
Glass surface definitions are centralized (two main primitives).
But “glass usage policy” is duplicated via component-specific borders/shadows/overlays:
Homepage adds seam + hover shadow
Header/footer add border and use glass-matte
Popup adds animate-in + shadow-soft
3.5 How a single reusable “Glass Surface system” could replace current implementation (report-only)
Conceptual replacement direction:

Define a surface primitive that composes:
glass base (matte/floating)
standardized border level
standardized elevation/shadow
standardized corner radii
standardized highlight/seam behavior
Then apply a single variant API (e.g., surface="matte|floating|overlay" + elevation="low|card|panel").
Current split exists between:
surface material (glass-matte vs glass-floating)
elevation/shadow (set ad hoc in components)

5.2 Border / divider logic
.seam-divider provides a pseudo-element overlay:
.seam-divider::after uses background: var(--border-seam) and box-shadow: var(--shadow-seam)
.seam-divider-h::after sets:
height: 1px; width: 100%; bottom: 0
.seam-divider-v::after sets:
width: 1px; height: 100%; right: 0
So:

On mobile (1-column): first two cards get a bottom seam divider.
On desktop (3-column): due to md:seam-divider-v, they become right-side seams.
5.3 Responsive layout behavior
Mobile:
single column

Desktop:

seams become vertical for first two cards (right 1px lines)

13. Architectural Simplification Opportunities (report-only)
13.1 Consolidate navigation into a single unified component
Maintenance benefit:

Reduce duplicated variant styling strings

13.2 Reusable Glass Surface system (beyond .glass-matte / .glass-floating)
Maintenance benefit:

13.4 Standardized borders + seams
