Phase 2 — Runtime Architecture & Canonicalization Audit Report
Executive Summary
This Next.js application exhibits a hybrid architecture with significant duplication between src and halden-ui directories. The application is in an active migration state, with the canonical design system located in halden-ui while the runtime application uses a mix of legacy components in site and newer components from the Halden UI library.

Key Findings:

Duplicate implementations exist for critical components (MobileDrawer, NavigationItem, cn utility)
Hybrid import patterns cross the src ↔ public boundary
26 unused components in halden-ui (DEAD branch)
Styling architecture is well-organized with canonical CSS in styles
No executable code violations in public (only component source files)
Migration is 60% complete for navigation, 0% for cards/hero/footer

Phase 8 — Folder Architecture Assessment
Executable Code in public/
Finding: YES - halden-ui contains 26 TypeScript/TSX component files.

Evidence: All files in components, lib, and constants are executable TypeScript code.

Convention Violation: YES - Next.js convention is that public should contain only static assets (images, fonts, etc.), not executable source code.

Recommendation: Move halden-ui to src/halden-ui/ or a separate package.

Folder Structure Evaluation

Long-Term Source of Truth
Recommended Structure:

src/ ├── app/ # Next.js App Router ├── components/ │ ├── site/ # Application-specific components │ └── halden-ui/ # Halden UI library (moved from public/) ├── lib/ # Utilities (cn, etc.) ├── hooks/ # Custom hooks (delete unused) ├── providers/ # Context providers (delete unused) └── types/ # TypeScript declarations

public/ # Static assets only ├── images/ ├── fonts/ └── favicon.ico

Rationale:

src/halden-ui/ becomes the canonical design system location
public reverts to static assets only (Next.js convention)
Clear separation between application code and library code
Easier to extract halden-ui to a separate package if needed
