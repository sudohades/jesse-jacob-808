# v2.10 Architectural Audit (Canonical Snapshot)

Last updated: 2026-07-14

> Purpose: single-source architectural snapshot for the current (stable) repository state. Prefer implementation evidence over historical investigation notes.

## 1) Repository Purpose (Current)
This repository is a Next.js (App Router) website that uses a layered UI architecture:

- **Halden UI** provides the canonical styling and a portable UI component set (tokens, CSS primitives, and React components).
- **Site components** provide the application-specific page composition (routing-ready shell, page headers, and branded integration).
- A thin **adapter layer** connects site-specific branding (e.g., logo integration + active navigation state) to Halden UI primitives.

The result is an implementation where visual system correctness (fonts, gradients, glass/motion styling) is driven by CSS variables and Halden UI style entrypoints, while React component ownership is organized by layer boundaries.

---

## 2) Architectural Evolution (Decisions, not Chronology)
### 2.1 Stabilization outcome
The stabilization effort converged on these structural decisions:

1. **Layered dependency direction**
   - Application → Site Components → Site Primitives → Utilities
   - Application → Halden UI Adapters → Halden UI (public) → Utilities
   - CSS tokens/styles are owned by Halden UI and imported by the application.

2. **Canonical “design tokens + primitives” styling model**
   - CSS variables define semantic palette + typography plumbing + hero gradient inputs.
   - Typography classes and primitives consume those variables.

3. **Adapter pattern for site-specific concerns**
   - Navigation is implemented as a site adapter that wraps Halden UI navigation and integrates the site’s branding and routing state.

### 2.2 What “stable” means in v2.10
- The runtime entrypoint loads the styling pipeline in a way that guarantees token variables exist before classes that depend on them.
- Typography and hero gradient behavior are driven by the token system (no scattered one-off gradients in app code).
- Ownership boundaries are documented and broadly respected (enforcement remains mostly convention-based).

## 3) Major Ownership Boundaries (Why these layers exist)

### 3.1 Brand Configuration → Platform Core → Halden UI
v2.10’s boundary concept is:

- **Brand Configuration**: site-specific brand inputs (logo, navigation labeling conventions, and page-level composition choices).
- **Platform Core**: the shared “platform” behaviors used by the site (token semantics, shared utilities, CSS entrypoint orchestration patterns).
- **Halden UI**: the canonical design system implementation (CSS tokens and component primitives).

In this codebase, these map practically to:
- Site-specific components in `src/components/site/` (Brand Configuration + site composition).
- Styling/token system in `src/styles/*` and (canonical) Halden UI CSS files imported from Halden UI style entrypoints.
- Portable primitives and tokens exported by Halden UI.

### Ownership rules (operational)
- **Halden UI owns**: typography primitives, glass/motion styling primitives, token semantics.
- **Site components own**: how pages are assembled (shell/header/footer/page headers) and where site branding is integrated.
- **Adapters own**: integrating site-only concerns into Halden UI (not rewriting Halden UI primitives).

## 4) Styling Architecture (CSS + Tokens + Typography)

### 4.1 CSS entrypoint orchestration
The runtime CSS chain is anchored by the application layout:

- `app/layout.tsx` imports **application** globals.
- `app/globals.css` exists as a styling orchestration file, but the runtime effective entrypoint is ultimately the one imported by layout.
- Halden UI CSS layers are imported via `@import` into the app-level CSS.

In the stabilized system, the important design is:
- **Single root CSS import chain** loads:
  - Tailwind utilities (needed for bracketed var utilities and gradient utilities)
  - Halden UI token CSS layers (theme + typography + glass + animations)
  - Application overrides and token aliasing required for font variables and hero variables.

### 4.2 Token organization
Tokens are split by responsibility:

- **Semantic palette + effects** (theme)
  - background/foreground muted colors
  - hairline borders, surface colors
  - radii/motion/shadows/grid
- **Hero inputs**
  - `--hero-text-start`, `--hero-text-middle`, `--hero-text-end`
  - `--hero-overlay-top`, `--hero-overlay-middle`, `--hero-overlay-bottom`, `--hero-overlay-focus`
- **Typography primitives inputs**
  - font variables exported by `next/font/google` (Quantico, Share Tech Mono, Inter)
  - application token aliases mapping Halden typography expectations to font variables

### 4.3 Typography recovery model
Typography stability relies on a three-step chain:

1. **Font variables exist**
   - `app/layout.tsx` loads fonts via `next/font/google` and attaches the generated CSS variables to `<html>`.
2. **App-level aliases exist**
   - Application global CSS aliases map “Halden typography expectations” to the font variables produced by `next/font`.
3. **Typography primitives exist**
   - Halden UI typography primitives declare classes (e.g. `.hd-h1..hd-h6`, display/body/eyebrow styles) that consume the aliased font variables.

Result: Halden UI typography primitives render deterministically.

### 4.4 Hero gradient architecture
Hero gradients are a token-driven system:

- Token inputs define gradient stops.
- A shared typography heading gradient primitive consumes hero token inputs.
- Components (e.g., headings in hero contexts) enable gradients via a `gradient` prop / class composition.

This removes “split brain” gradients (app-specific Tailwind gradients vs system gradients).

## 11) Stable Callback Contracts

### 11.1 Why callback identity matters
Reusable components that receive callbacks as props should have stable callback identities unless the callback's behavior intentionally changes. When callbacks are recreated on every parent render, child component effects that depend on those callbacks will rerun unnecessarily, causing:

- Unnecessary event listener attachment/detachment cycles
- Unnecessary effect cleanup and re-execution
- Potential performance degradation
- Misleading ESLint React Hook warnings

Effects should depend on behavior, not incidental function recreation.

### 11.2 Stable callback implementation pattern
When a callback's implementation is stable (doesn't change across renders), memoize it using `useCallback`:

```tsx
// Correct: stable callback identity
const onClose = React.useCallback(() => setOpen(false), []);

// Incorrect: new function on every render
const onClose = () => setOpen(false);
```

The dependency array should only include values that the callback's behavior actually depends on. React guarantees that `setState` functions from `useState` have stable identity, so they don't need to be included in dependency arrays.

### 11.3 Architectural decision for SiteNavigation/MobileDrawer
The `onClose` callback passed from `SiteNavigation` to `MobileDrawer` was memoized using `useCallback` with an empty dependency array because:

- The callback implementation never changes (always calls `setOpen(false)`)
- It only depends on `setOpen`, which React guarantees is stable
- The effect in `MobileDrawer` depends on `onClose` and should only rerun when drawer state changes
- This preserves MobileDrawer's ownership of Escape-key behavior (drawer-specific concern)
- This maintains the public component API and runtime behavior

### 11.4 Guidance for Halden UI component callbacks
When passing callbacks to reusable Halden UI components:

1. **Memoize stable callbacks**: Use `useCallback` when the callback's behavior doesn't change
2. **Include only semantic dependencies**: List only values that affect the callback's behavior
3. **Respect component ownership**: Don't move behavior into parent components to avoid memoization
4. **Preserve reusability**: Components should remain reusable across different contexts

This ensures effects in reusable components rerun only when semantically required, not when parent components rerender for unrelated reasons.

## 12) Production Styling Investigation (2026-07-15)

### 12.1 Issue description
Production deployment lost glassmorphism blur on the navigation bar:
- Development environment: proper glass blur rendered correctly
- Production deployment: transparent background, noise texture visible, backdrop blur absent

### 12.2 Canonical runtime trace
The glass styling chain:
- `app/layout.tsx` → imports `@/styles/globals.css`
- `app/page.tsx` → renders `SiteShell`
- `src/components/site/SiteShell.tsx` → renders `SiteHeader`
- `src/components/site/SiteHeader.tsx` → renders `SiteNavigation`
- `src/components/halden-ui/navigation/SiteNavigation.tsx` (line 66) → applies `hd-glass hd-glass--nav` when scrolled
- `src/styles/glass.css` (lines 50-55) → defines `.hd-glass--nav` with backdrop-filter
- `src/styles/theme.css` (line 57) → defines `--blur-lg: 38px`

### 12.3 Root cause
Tailwind CSS v4's PostCSS plugin was removing the standard `backdrop-filter` property during production optimization while keeping only the `-webkit-backdrop-filter` prefixed version. Modern browsers require the standard property to render backdrop blur.

**Evidence:**
- Source CSS (`src/styles/glass.css` line 42): contained both `backdrop-filter` and `-webkit-backdrop-filter`
- Compiled CSS (`.next/static/css/5d46743eefeb9f5b.css`): only `-webkit-backdrop-filter` remained
- Same pattern occurred for `.hd-glass`, `.hd-glass--soft`, and `.hd-glass--nav`

### 12.4 Why local differed from production
Development builds do not apply the same CSS optimization/purging that production builds do. The Tailwind CSS v4 PostCSS plugin optimizes CSS by removing unprefixed properties when prefixed versions exist, assuming the prefix is sufficient. This assumption is incorrect for modern browsers that require the standard property.

### 12.5 Minimal fix applied
Wrapped standard `backdrop-filter` declarations in `@supports` queries to force preservation during optimization:

```css
.hd-glass--nav {
  background: color-mix(in oklab, var(--color-background) 70%, transparent);
  -webkit-backdrop-filter: blur(var(--blur-lg)) saturate(150%);
  border-radius: var(--radius-md);
}

@supports (backdrop-filter: blur(1px)) {
  .hd-glass--nav {
    backdrop-filter: blur(var(--blur-lg)) saturate(150%);
  }
}
```

Applied to:
- `.hd-glass` (base glass)
- `.hd-glass--soft` (soft variant)
- `.hd-glass--nav` (navigation variant)

### 12.6 Verification
Post-fix production build (`.next/static/css/932fcda3cd64e765.css`) confirmed:
- `backdrop-filter:blur(var(--blur-lg))` now present in compiled CSS (3 occurrences)
- Build succeeds without errors
- Halden UI remains sole owner of glass styling
- No duplicate styling introduced

### 12.7 Mobile navigation arrow direction
Fixed mobile navigation drawer arrows to point right (→) instead of left (←) to communicate forward navigation into content:
- Changed in `src/components/halden-ui/navigation/MobileDrawer.tsx` line 62
- Preserved all existing layout, spacing, animation, and interaction behavior
